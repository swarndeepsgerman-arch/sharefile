What is Machine Creation Services?

MCS is Citrix's hypervisor-agnostic provisioning technology that creates and manages pools of virtual machines from a single master image — without requiring a dedicated provisioning server.

Core concept — the 3-layer model
1Master Image VM
→
2Snapshot
→
3MCS Catalog
→
4Cloned VMs (provisioned)
→
5Users connect via Broker

MCS calls the hypervisor API directly — no PVS server, no TFTP, no network streaming required.

Identity disk

A tiny ~16 MB virtual disk attached to each VM holding the unique machine SID, computer name, and AD account. Gives each clone its own identity while sharing the base OS image.

Shared base disk

All VMs in a non-persistent catalog share a single read-only copy of the base OS disk. This drastically reduces storage consumption and eliminates duplicate I/O during boot storms.

Write-back cache disk

Stores all runtime writes from the VM — in RAM, on disk, or both. For non-persistent VMs, the cache is discarded on reboot. For persistent VMs, changes accumulate over time.

Hypervisor API-driven

MCS communicates with the underlying hypervisor or cloud platform via the Hosting Connection. No agent on the hypervisor is required — it uses native APIs (vSphere, Azure ARM, AWS EC2).

MCS Architecture

Understanding the control plane, data plane, and how MCS integrates with the Citrix CVAD platform.

Key insight The Delivery Controller's MCS service is the orchestrator — it receives provisioning instructions from Studio, translates them into hypervisor API calls (e.g., clone VM, attach disk, create AD account), and tracks the state of all provisioned machines in the Site Database.

Machine catalog types

Choosing the right catalog type is the single most important design decision in an MCS deployment. Each type has distinct storage, performance, and management implications.

01

Non-persistent / Pooled Random

Recommended for most deployments

Every session gets a clean VM. On logoff or reboot the VM resets to the master image state — all writes are discarded. User data and settings are preserved separately via profile management.

Write-back cache options
RAM only
Fastest. Lost on reboot. Use for short sessions with very low write activity.
RAM + disk overflow ✓
Recommended. RAM absorbs bursts; disk handles overflow. Cleared on reboot.
Disk only
Use when RAM is constrained. Slower but reliable. No crash risk from RAM exhaustion.
Best for
Task workersCall centresShared desktopsPublished apps (RDSH)Kiosk / hot-desk
Mandatory companionFSLogix Profile Containers are required with non-persistent VMs. Without profile management, all user settings, Outlook cache, browser data, and Teams/OneDrive state are lost on every reboot.
02

Persistent / Static Assigned

Use only where required

Each user is permanently assigned to their own VM. Writes persist to the VM's difference disk — the machine builds up a personal state over time. Requires more storage and complex patching.

Best for
Power usersDevelopersUsers who install custom appsLegacy apps requiring local state
Storage warningPersistent VMs consume significantly more storage — each VM accumulates a growing difference disk. Patching is complex: each VM must be patched individually rather than updating a shared master image. Evaluate carefully before choosing this type.
03

MCS I/O Optimisation (Storage Optimisation)

Enable for all non-persistent catalogs

An enhancement to non-persistent MCS that uses a shared read-only base disk, dramatically reducing storage consumption and eliminating redundant I/O during boot storms.

Without MCS I/O
100 VMs × 60 GB OS disk = 6 TB storage. Each VM has a full OS disk copy.
With MCS I/O ✓
~60 GB shared base + thin WBC per VM. 90%+ storage reduction for large catalogs.
RequirementMCS I/O driver must be installed on the master image (select during VDA installation). Enabled at catalog creation time — cannot be retroactively applied to existing catalogs.

Prerequisites & preparation

Get these right before creating your first catalog — skipping any step causes provisioning failures or degraded performance.

Master image preparation checklist

  • Install and fully patch the Windows OS (Server 2022 for RDSH, Windows 11 for VDI). Join the domain before installing the VDA.
  • Install the correct VDA type: Server OS VDA for RDSH multi-session; Desktop OS VDA for single-session VDI.
  • Select "MCS I/O" driver during VDA installation if using storage optimisation (recommended).
  • Run Citrix Optimizer — select the correct OS + VDA version template. This disables unnecessary services and reduces resource consumption.
  • Disable Windows Update on the image — manage patching via WSUS or by updating and re-snapshotting the golden image.
  • Install all required applications and configure them to the desired baseline state.
  • Clear event logs, temp files (%TEMP%, C:\Windows\Temp), and browser caches before snapshot.
  • Do NOT run Sysprep — MCS handles machine identity via the identity disk. Sysprep is not required and may break VDA registration.
  • Shut down cleanly before taking the hypervisor snapshot. Never snapshot a running VM for MCS use.

Active Directory & OU preparation

Dedicated MCS OU structure

Creating a machine catalog

Step-by-step walkthrough of the Citrix Studio wizard and its PowerShell equivalent.

Studio wizard — step by step

1

Operating system type

Server OS = Windows Server (RDSH multi-session apps/desktops). Desktop OS = Windows 10/11 (single-session VDI). This determines the VDA type required and the Citrix license consumed per session.

2

Machine management

Select "Machines that are power managed" → "Citrix Machine Creation Services". Choose the hosting connection (vSphere / Azure / etc) that MCS will use to call the hypervisor API.

3

Desktop experience (allocation type)

Pooled-random = non-persistent (recommended). Static = persistent. This controls whether CleanOnBoot is set on the provisioning scheme — it cannot be changed after catalog creation.

4

Master image selection — critical step

Select the snapshot, not the live VM. MCS stores a reference to the snapshot path in the Site DB. If you later delete the snapshot from the hypervisor, catalog updates will fail. Always keep at least 2 previous snapshots.

5

Storage & MCS I/O

Select datastores for OS disk and write-back cache (can be separate — recommended). Enable MCS I/O Optimisation here. For vSphere, choose storage profiles if using vSAN storage policies. Set WBC disk size (10–40 GB) and RAM cache size (256 MB–1 GB).

6

VM size & count

Set vCPU count and RAM per VM. Specify how many VMs to provision. Note: you can add more machines later — provisioning more upfront is not required.

7

AD machine accounts & naming scheme

Select the target OU for machine computer accounts. Define the naming scheme (e.g., VDI-###). MCS will auto-create and manage AD computer accounts — no manual pre-staging required.

✓

Summary & provision

Review all settings. MCS creates VMs in the hypervisor. VMs do not register with the Broker until first power-on, when the VDA contacts the Delivery Controller and completes registration.

PowerShell provisioning — complete script

PowerShell / CVAD SDK — full catalog creation
Add-PSSnapin Citrix.* -ErrorAction SilentlyContinue

# 1. Create identity pool (defines AD account creation settings)
$idPool = New-AcctIdentityPool `
  -IdentityPoolName "VDI-Pool-01" `
  -NamingScheme "VDI-###" `
  -NamingSchemeType Numeric `
  -OU "OU=MCS-Pooled,DC=domain,DC=com" `
  -Domain "domain.com"

Write-Host "Identity pool created: $($idPool.IdentityPoolName)"

# 2. Create provisioning scheme (links to master image snapshot)
$provTask = New-ProvScheme `
  -ProvisioningSchemeName "VDI-Pool-01" `
  -HostingUnitName "vSphere-Cluster01" `
  -MasterImageVM "XDHyp:\HostingUnits\vSphere-Cluster01\MasterVMs\Win11-Gold.vm\Snap-2025-05.snapshot" `
  -VMCpuCount 2 `
  -VMMemoryMB 4096 `
  -CleanOnBoot `                       # non-persistent: reset writes on reboot
  -UseWriteBackCache `
  -WriteBackCacheDiskSize 20 `         # GB
  -WriteBackCacheMemorySize 512 `      # MB RAM cache
  -RunAsynchronously

# Wait for scheme creation to complete
while ((Get-ProvTask -TaskId $provTask.TaskId).Active) {
    Write-Host "Creating provisioning scheme..."
    Start-Sleep -Seconds 5
}

$provScheme = Get-ProvScheme -ProvisioningSchemeName "VDI-Pool-01"

# 3. Create the broker catalog
$catalog = New-BrokerCatalog `
  -Name "VDI-Pool-01" `
  -AllocationType Random `             # Pooled-random = non-persistent
  -PersistUserChanges Discard `        # Discard writes on reboot
  -ProvisioningSchemeId $provScheme.ProvisioningSchemeUid `
  -SessionSupport SingleSession `      # SingleSession for VDI, MultiSession for RDSH
  -MachineType Virtual

# 4. Create AD computer accounts
Write-Host "Creating AD accounts..."
$adAccounts = New-AcctADAccount `
  -IdentityPoolName "VDI-Pool-01" `
  -Count 20

Write-Host "Created $($adAccounts.SuccessfulAccounts.Count) AD accounts"

# 5. Provision VMs in the hypervisor
$provTask = New-ProvVM `
  -ProvisioningSchemeName "VDI-Pool-01" `
  -ADAccountName $adAccounts.SuccessfulAccounts `
  -RunAsynchronously

while ((Get-ProvTask -TaskId $provTask.TaskId).Active) {
    $task = Get-ProvTask -TaskId $provTask.TaskId
    Write-Host "Provisioning VMs... $($task.TerminatingError)"
    Start-Sleep -Seconds 10
}

# 6. Register provisioned VMs with the Broker
$provVMs = Get-ProvVM -ProvisioningSchemeName "VDI-Pool-01"
foreach ($vm in $provVMs) {
    New-BrokerMachine `
      -CatalogUid $catalog.Uid `
      -MachineName $vm.ADAccountName
}

Write-Host "Done! $($provVMs.Count) VMs provisioned and registered."

Updating the master image

Rolling out image updates is the most frequent MCS maintenance task. Understanding the pipeline prevents outages.

Image update pipeline
1Update master VM
→
2Shut down & snapshot
→
3Update catalog in Studio
→
4Rollout to VMs
→
5VMs reboot with new image

On next shutdown Recommended

VMs get the updated image on their next natural reboot. Zero immediate disruption to active sessions. Ideal for production environments.

Scheduled rollout

Schedule Studio to force reboots during a maintenance window (e.g., 2 AM Sunday). Session drain + reboot in controlled waves.

Immediate (force)

Studio forces VMs off immediately. Terminates all active sessions. Use only in emergency maintenance windows.

Rollback — reverting to a previous image

Because MCS uses snapshots as its source, rolling back is simply pointing the catalog back to the previous snapshot — no data migration, no re-provisioning. The fastest rollback in the business.

PowerShell — rollback and automated image update
# ── ROLLBACK to previous snapshot ──
Set-ProvScheme `
  -ProvisioningSchemeName "VDI-Pool-01" `
  -MasterImageVM "XDHyp:\HostingUnits\vSphere\MasterVMs\Win11.vm\Snap-2025-04.snapshot"

Write-Host "Rollback staged. VMs will use previous image on next reboot."

# ── AUTOMATED UPDATE SCRIPT ──
param(
  [string]$CatalogName  = "VDI-Pool-01",
  [string]$NewSnapshot  = "XDHyp:\HostingUnits\vSphere\MasterVMs\Win11.vm\Snap-2025-05.snapshot"
)

Add-PSSnapin Citrix.* -ErrorAction SilentlyContinue

# Stage the new image
Set-ProvScheme -ProvisioningSchemeName $CatalogName -MasterImageVM $NewSnapshot
Write-Host "[$(Get-Date -f 'HH:mm:ss')] New image staged: $NewSnapshot"

# Get all idle machines not already in maintenance
$machines = Get-BrokerMachine -CatalogName $CatalogName |
  Where-Object { $_.SessionCount -eq 0 -and -not $_.InMaintenanceMode }

Write-Host "[$(Get-Date -f 'HH:mm:ss')] Found $($machines.Count) idle machines — initiating rollout"

foreach ($m in $machines) {
    Set-BrokerMachineMaintenanceMode -InputObject $m -MaintenanceMode $true
    New-BrokerHostingPowerAction -MachineName $m.DNSName -Action Restart
    Write-Host "  → Restarting $($m.MachineName)"
    Start-Sleep -Seconds 3
}

Write-Host "[$(Get-Date -f 'HH:mm:ss')] Rollout complete. Monitor with:"
Write-Host "  Get-BrokerMachine -CatalogName $CatalogName | Group-Object ImageOutOfDate"
Snapshot retention policy Keep a minimum of 2 previous snapshots before deleting old ones. Never delete a snapshot referenced by an active provisioning scheme — MCS cannot stage updates without the source snapshot, and the deletion is irreversible.

Write-back cache deep dive

Write-back cache (WBC) is central to non-persistent MCS performance. Misconfiguration is the most common cause of session crashes and performance problems.

How write-back cache works
VM writes data
→
Intercepted by MCS I/O driver
→
Stored in RAM cache first
→
Overflow to WBC disk if RAM fills
→
Discarded on VM reboot

Base disk remains read-only throughout the session. The MCS I/O driver transparently merges reads from the base disk with writes from the cache, making it invisible to the OS.

Sizing guidance

RAM cache
256 MB – 1,024 MB. Start with 256 MB for task workers, 512 MB for knowledge workers. Increase if you see elevated disk write latency during sessions.
Disk cache
10–40 GB per VM. Task workers: 10–15 GB. Knowledge workers: 20–30 GB. Add 15 GB if Windows Update may run during sessions.
Cache disk storage
Place on SSD or NVMe datastore. WBC is write-intensive — spinning disk causes severe performance degradation at scale.
vSAN consideration
Set Flash Read Cache Reservation = 0% for WBC disk storage policy. WBC is write-heavy; read caching provides no benefit.
Critical risk If the RAM cache fills and the overflow disk also fills completely, the VM session will crash immediately with no warning. Monitor WBC utilisation proactively — alert at 70% disk usage. Proactive reboots of idle non-persistent VMs clear the cache and reset the counter.
Monitor WBC utilisation across all VMs
# Report WBC disk utilisation per VM — sort by highest usage
Get-ProvVM -ProvisioningSchemeName "VDI-Pool-01" | ForEach-Object {
    $vmName = $_.VMName
    $wbcDisk = Get-ProvDisk -VMName $vmName |
               Where-Object { $_.IsWriteBackCacheDisk }
    if ($wbcDisk) {
        [PSCustomObject]@{
            VMName      = $vmName
            TotalGB     = [math]::Round($wbcDisk.DiskSize / 1GB, 1)
            UsedGB      = [math]::Round($wbcDisk.InUse / 1GB, 1)
            FreeGB      = [math]::Round(($wbcDisk.DiskSize - $wbcDisk.InUse) / 1GB, 1)
            UsedPct     = [math]::Round($wbcDisk.InUse / $wbcDisk.DiskSize * 100, 1)
        }
    }
} | Sort-Object UsedPct -Descending | Format-Table -AutoSize

Troubleshooting common issues

Structured diagnostic approach to the most frequent MCS failures — from provisioning errors to VDA registration problems.

01
VMs provisioned but not registering — "Unregistered" state
Diagnostic command
Get-BrokerMachine -CatalogName "VDI-Pool-01" |
  Select MachineName, RegistrationState, LastDeregistrationReason |
  Format-Table -AutoSize
Common causes & fixes
Firewall blocking
TCP 80/443 must be open from VM to Delivery Controller. Check Windows Firewall and network ACLs.
DNS resolution failure
VM cannot resolve Controller FQDN. Test: nslookup <controller-fqdn> from inside the VM.
VDA version mismatch
VDA must be equal to or newer than the Controller's minimum supported version. Update VDA on master image and reprovision.
ListOfDDCs misconfigured
Check registry: HKLM\SOFTWARE\Citrix\VirtualDesktopAgent — ListOfDDCs must contain correct Controller FQDNs.
Key log location on the VM: Event Viewer → Applications and Services Logs → Citrix → Virtual Desktop Agent. Event ID 1004 = Registered successfully. Event ID 1012 = Registration failed (reason in detail).
02
Catalog update fails — "master image not found" or "snapshot path invalid"

The snapshot referenced by the provisioning scheme has been deleted from the hypervisor. MCS cannot stage the update because the source no longer exists.

# Identify what snapshot the scheme currently references
Get-ProvScheme -ProvisioningSchemeName "VDI-Pool-01" |
  Select ProvisioningSchemeName, MasterImageVM

# Point to a valid existing snapshot
Set-ProvScheme `
  -ProvisioningSchemeName "VDI-Pool-01" `
  -MasterImageVM "XDHyp:\HostingUnits\vSphere\MasterVMs\Win11.vm\ValidSnap.snapshot"
PreventionNever delete a hypervisor snapshot that is referenced by an active MCS provisioning scheme. The snapshot reference is stored in the Site DB — deletion on the hypervisor side does not auto-update the reference. Keep 2+ old snapshots before deleting any.
03
Boot storm — VMs taking too long to provision or boot

Simultaneous VM provisioning or power-on saturates storage IOPS, causing long delays and potential timeouts.

Enable MCS I/O optimisation
Shared read base eliminates duplicate OS disk reads. Single biggest improvement for boot storm reduction.
Stagger power-on
Use power management schedules to power VMs on in waves (e.g., 10 VMs every 30 seconds), not all simultaneously.
Separate datastores
Put OS base disks and WBC disks on different datastores or storage tiers to distribute IOPS load.
Pre-launch in advance
Use Delivery Group power management to boot VMs 30–60 minutes before peak hours so they are warm when users connect.
04
Non-persistent VMs not resetting on reboot — writes persisting

The CleanOnBoot flag is not set on the provisioning scheme, or the MCS I/O driver is not installed on the master image.

# Verify CleanOnBoot setting
Get-ProvScheme -ProvisioningSchemeName "VDI-Pool-01" |
  Select ProvisioningSchemeName, CleanOnBoot

# Verify MCS I/O driver in Device Manager on master VM:
# Device Manager → Citrix MCS Storage Driver must be present

# CleanOnBoot CANNOT be changed on existing schemes.
# You must create a new catalog with the correct setting.
Cannot change in-placeCleanOnBoot cannot be modified on an existing provisioning scheme. If set incorrectly, create a new catalog with the correct setting, migrate the Delivery Group, then decommission the old catalog.
05
Session crashes — "No disk space" or VM becomes unresponsive

The write-back cache disk has reached capacity. When both RAM and disk cache are exhausted, the VM session crashes immediately with no user warning.

# Identify VMs with high WBC disk utilisation
Get-ProvVM -ProvisioningSchemeName "VDI-Pool-01" | ForEach-Object {
    $d = Get-ProvDisk -VMName $_.VMName |
         Where-Object { $_.IsWriteBackCacheDisk }
    if ($d) {
        [PSCustomObject]@{
            VM      = $_.VMName
            UsedPct = [math]::Round($d.InUse / $d.DiskSize * 100, 1)
            FreeGB  = [math]::Round(($d.DiskSize - $d.InUse) / 1GB, 1)
        }
    }
} | Where-Object { $_.UsedPct -gt 70 } | Sort-Object UsedPct -Descending

Immediate fix: Reboot idle sessions to clear the WBC disk. Long-term fix: Increase WBC disk size in the provisioning scheme and re-provision affected VMs, or investigate what process is generating excessive writes (Windows Update, antivirus scans).

Best practices

Architectural and operational recommendations from real-world MCS deployments at scale.

Master image hygiene

▪ One image per purpose — separate RDSH and VDI master images. Never mix OS types in one catalog.

▪ Always run Citrix Optimizer before snapshotting. Select the exact OS + VDA version template.

▪ Name snapshots with date and patch level: Win11-22H2-2025-05-Patch

▪ Test in a dev/test catalog first — never push untested images directly to production.

▪ Keep minimum 2 previous snapshots before deleting any old ones.

Storage architecture

▪ Always enable MCS I/O Optimisation for non-persistent catalogs — 90%+ storage reduction.

▪ Place OS base disks and WBC disks on separate datastores to distribute IOPS.

▪ SSD or NVMe is mandatory for WBC disks — spinning disk causes session degradation at scale.

▪ On vSAN: use Flash Read Cache Reservation = 0% for WBC storage policy (write-heavy, read cache irrelevant).

FSLogix profile pairing

▪ FSLogix Profile Containers are mandatory with non-persistent MCS — they make VMs feel persistent to users.

▪ VHDX format, dynamic sizing. Start at 30 GB for knowledge workers; adjust per workload.

▪ Place profile shares on HA file servers (Scale-Out File Server or Azure Files for cloud). Profile share unavailability prevents logon.

▪ Set DeleteLocalProfileWhenVHDShouldApply = 1 to ensure the container always takes precedence.

Capacity & power management

▪ Maintain a buffer pool: keep 10–20% of VMs powered on and idle at all times to absorb demand spikes without logon delays.

▪ Schedule off-peak VM shutdown to reduce storage I/O and hypervisor overhead overnight.

▪ For RDSH: schedule nightly reboots to apply image updates and clear accumulated memory leaks.

▪ Alert when available machines drop below 5% of catalog size — signals an urgent need to add capacity.

▪ Use Citrix Director or ControlUp for real-time monitoring of session health, login times, and resource utilisation.

FSLogix configuration quick reference

HKLM\SOFTWARE\FSLogix\Profiles — recommended settings
Enabled                              = 1        ; Enable FSLogix
VHDLocations                         = \\fileserver\profiles\%username%
DeleteLocalProfileWhenVHDShouldApply = 1        ; VHD always wins
SizeInMBs                            = 30720    ; 30 GB — adjust per user type
VolumeType                           = VHDX     ; VHDX preferred over VHD
IsDynamic                            = 1        ; Thin-provisioned VHDX
ConcurrentUserSessions               = 1        ; Allows multiple sessions
PreventLoginWithFailure              = 0        ; Allow logon even if VHD unavailable (fallback)
SetTempToLocalPath                   = 2        ; Redirect TEMP to local disk (performance)
